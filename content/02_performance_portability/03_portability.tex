\section{What Is Portability?}
\label{sec::portability}

When we are talking about portability, we can distinguish between two basic forms of portability. 
On the one hand, binary portability means that I compile my code once, and it runs everywhere. 
On the other hand, source code portability means I write portable source code that does not need to be changed when targeting a new hardware platform but must be recompiled on said new hardware platform. 
Generally, the former is much more challenging to achieve than the latter. %, and most of the time, some form of \gls{jit} compilation is involved. 
For the remainder of this thesis, if I talk about portability, I mean source code portability. 

The need for portable codes, in general, has been an ongoing problem for many years. 
One of the first portability definitions was already provided in \citeyear{poole_portability_1975}, fifty years ago: 
\begin{quotebox}{\citet{poole_portability_1975}}
    Portability is a measure of the ease with which a program can be transferred from one environment to another: If the effort required to move the program is much less than that required to implement it initially, then we say that it is highly portable.
\end{quotebox}

The definition of portability of \citet{poole_portability_1975} was later slightly modified to ... by \citet{mooney_strategies_1990, mooney_bringing_1997}:
\begin{quotebox}{\citet{mooney_bringing_1997}}
    A software unit is portable (exhibits portability) across a class of environments to the degree that the cost to transport and adapt it to a new environment in the class is less than the cost of redevelopment. 
\end{quotebox}
This definition is closely related to the definition from \citet{poole_portability_1975}. 
It is only slightly more precise in specifying that any software unit, including library codes instead of only programs, can be portable. 
Additionally, it narrows down the portability considerations to environments of the same class.  

Based on the definition from \citet{mooney_strategies_1990, mooney_bringing_1997}, \citet{sedova_high-performance_2018} devised a formal definition of portability:
\begin{definition}[Portability~\cite{sedova_high-performance_2018}]
An application can be said to be portable if the cost of porting is less than the cost of re-writing:
$$DP = 1 - \left(\frac{C_P}{C_R}\right)$$
where $C_P$ is the cost to port, and $C_R$ is the cost to rewrite the program. 
\end{definition}
A program is completely portable if $DP$ is one, and a positive value indicates that porting a code is more profitable than rewriting it from scratch. 
However, devising such costs is highly non-trivial and subjective. 
Is the cost only based on the amount of lines of code that must be changed? 
That can be easily measurable but does not really reflect true real-world cost since it also depends on the development time necessary to port a code. 
If we factor in development time, we also have to account for the developers' different experience levels: a developer already familiar with a new hardware platform may port a code in less time than an unfamiliar programmer, reducing the real-world cost of porting and, therefore, changing the cut-off point of when porting a code may be worthwhile. 
However, it is extremely difficult to assess the developers' different experience levels beforehand to decide whether porting or rewriting an application is more feasible. 

A more recent definition of portability was created by \citet{pennycook_metric_2016, pennycook_implications_2019} which define portability as: 
\begin{quotebox}{\citet{pennycook_implications_2019}}
    The ability of an application to execute a problem correctly on a given set of platforms.
\end{quotebox}
In contrast to the previous definition, the key part here is that it is not enough for an application to run on different hardware platforms but to produce the correct results on these different platforms. 
An application that runs everywhere but produces wrong results is pointless in a real-world setting.

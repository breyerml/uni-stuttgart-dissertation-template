\chapter{The Hardware Sampling Library: hws}
\label{chapter:hws}

In \autoref{sec:performance}, \nameref{sec:performance}, I mainly focused on the \acrfull{flops} or memory bandwidth of a code. 
However, to gain more insights into an application's performance and especially efficiency, it is also important to examine various other hardware-related metrics, such as utilization, power consumption, memory consumption, or temperatures independent of the hardware platform. 
Only with knowledge about these can we answer questions like: Do we utilize our hardware as we expected? Are we subject to clock or thermal throttling? How much power do we use on the \gls{cpu} or \gls{gpu}? Does my application need more memory than expected? Do we have too many memory allocations? 
Especially gathering information about energy consumption gets more and more important in the age of \glspl{llm}, with the ever-increasing number of parameters and supercomputers that get bigger and bigger~\cite{de_vries_growing_2023, luccioni_estimating_2023}. 
For example, the current top three supercomputers in the TOP500 list~\cite{top500org_november_2024} have an accumulated power draw of nearly $\SI{93}{\mega\watt}$. 
To put this into perspective, one would need $\num{34}$ average onshore wind turbines, having a capacity of $\SI{2.75}{\mega\watt}$ each, to fulfill this power capacity. 
Note that in practice in the US, on average, only $\SI{42}{\percent}$ of this theoretical capacity is achieved, meaning that in reality, this number would be closer to $\num{80}$ wind turbines to operate the three biggest supercomputers if they are running at their peak capacity~\cite{usgs_how_2022}. 
Yet, gathering this information in a vendor-independent way for different hardware platforms, especially if we consider any \gls{cpu}, or \glspl{gpu} from NVIDIA, \gls{amd}, or Intel, is not as straightforward as it initially seems. 

\begin{listing}
    \begin{moderncode}[fontsize=\small]{c++}
// NVIDIA - NVML
unsigned long long power{};  // mJ
nvmlReturn_t errc = nvmlDeviceGetTotalEnergyConsumption(device_handle, &power);

// AMD - ROCm SMI library
[[maybe_unused]] std::uint64_t timestamp{};
float resolution{};
uint64_t value{};  // @$\mu$@J
rsmi_status_t errc = rsmi_dev_energy_count_get(device_handle, &value, &resolution, &timestamp);
float power = value * resolution;

// Intel - Level Zero
std::uint32_t num_power_domains{};  // @$\mu$@J
// get the number of available power domains
if (zesDeviceEnumPowerDomains(device_handle, &num_power_domains, nullptr) == ZE_RESULT_SUCCESS) {
    power_handles.resize(num_power_domains);
    // enumerate the available power domains
    if (zesDeviceEnumPowerDomains(device_handle, &num_power_domains, power_handles.data()) == ZE_RESULT_SUCCESS) {
        // we found at least one power domain
        if (!power_handles.empty()) {
            // get the total power consumption of the first power domain
            zes_power_energy_counter_t energy_counter{};
            if (zesPowerGetEnergyCounter(power_handles.front(), &energy_counter) == ZE_RESULT_SUCCESS) {
                std::uint64_t power = energy_counter.energy;
            }
        }
    }
}
    \end{moderncode}

While all hardware vendors provide some form of gathering this information through custom libraries, they do not agree to a standardized interface. 
As an example, to gather the total power consumption (since the last driver reload) for NVIDIA, \gls{amd}, and Intel \glspl{gpu}, the library functions shown in \autoref{code:vendor_library_calls} must be used.
It shows two major problems in gathering such information in a vendor-independent way. 
First, as already mentioned, the \glspl{api} greatly differ between the different vendors. 
For example, using \gls{nvml}, collecting the total power consumption can be done in two lines of code (lines 2+3); when using Intel's Level Zero, on the other hand, we at least need twelve lines of code (lines 13-28). 
Second, the libraries do not even agree on the same physical unit: While \gls{rocmsmi} and Level Zero both report the total power consumption in $\si{\mu\joule}$, NVIDIA's \gls{nvml} library reports it in $\si{\milli\joule}$.
An additional challenge is that for some information, like total power consumption, it may be sufficient to report only the final value for the whole application, but for other information, like the clock frequency or temperatures, it is necessary to sample the information during the whole program execution to get a more fine-grained view of the application. 


A few libraries already exist that solve at least some of these problems. 
However, they are all restricted in one way or another.
For example, the smaller libraries all support only a small subset of the possible hardware we are interested in: 
\cite{araf_verified_2020, leinardi_greenwithenvy_2024, noauthor_gpu_2024, guerreiro_gpgpu_2018} only support NVIDIA \glspl{gpu}, \cite{amd_amd_2024, noauthor_gpu_2023} only support \gls{amd} \glspl{gpu}, \cite{noauthor_ricks-lab_2024} supports NVIDIA and \gls{amd} \glspl{gpu}, \cite{benoit_courty_mlco2codecarbon_2024} supports NVIDIA and Intel \glspl{gpu}, \cite{noauthor_libgpucounters_2024} supports ARM Immortalis and Mali \glspl{gpu}, and \cite{google_hardwareperfcounter_2022} supports Adreno and Mali \glspl{gpu}.

The larger libraries do support more different hardware platforms, but they also do not support the hardware we are interested in (with one exception). 
\gls{papi}~\cite{mucci_papi_1999} supports low-level performance counters to get various information from different \glspl{cpu} as well as NVIDIA and \gls{amd} \glspl{gpu}. 
Likwid~\cite{thomas_gruber_likwid_2023} is similar to \gls{papi} in that it also supports low-level performance counters for different hardware. 
Its main focus lies on \glspl{cpu}, but NVIDIA and \gls{amd} \glspl{gpu} are also supported, although officially only in an experimental state. 
Using Likwid's marker \gls{api}, gathering performance counter information can be limited to only the parts of the code we are currently interested in. 
The PowerAPI~\cite{fieni_powerapi_2024} is a collection of different tools that can be used to measure and analyze the power consumption of applications and the power consumption only. 
It supports \glspl{cpu} and \glspl{gpu} from Intel and NVIDIA \glspl{gpu}. 
VARIORUM~\cite{noauthor_variorum_2024} is the only library that supports generic wrappers around low-level \gls{api} functions for all major \gls{cpu} and \gls{gpu} vendors. 
Through its \code{var_monitor}, it also supports sampling information of a whole compute node at a fixed interval. 
However, none of these libraries support vendor-independent sampling of hardware information for all major hardware platforms so that the user can programmatically specify what should be sampled and when sampling should be paused or stopped. 

Therefore, I wrote the hardware sampling library \textit{hws}~\cite{breyer_hws_2024-1, breyer_hardware-independent_2024, breyer_hws_2024} that also wraps the low-level functions from all major hardware vendors and additionally exposes an easy-to-use sampling interface to be able to automatically gather all necessary information during the whole program execution. 
In the following subsections, I will introduce what the hws library can sample and how it is implemented. 
This chapter is concluded with a small example of how to use hws.
